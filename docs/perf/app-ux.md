# macOS transcript: phase 1

Child spawns now become one typed child operation shared by the macOS app,
TUI and web client. Each operation has a status, short work title, result
summary and navigation to its own session. Stored output has a size label
and an **Open output** action. Native scrolling retains the visible item
through external updates and adjacent history delivery, and follows new
output only at the actual viewport bottom.

Phase 1 implementation and local verification are complete. The owner's
white-space screenshot is still pending: that symptom has not been attributed
or claimed fixed. Full CI has not been dispatched; phase 2 requires instruction.

## Reproduction and root causes

The baseline is `5610d9e021bbf83044a80974c7f6eac147fa2564`, PROTO 43,
with the release native app, release fixture-enabled helper and isolated
real daemon using the echo agent. Short, large, parallel, fork and background
spawns were exercised without a provider request.

- A short spawn produced a tool row at key 4 and a child row at key 5 for
  one operation. Two parallel spawns produced two tool rows and two child
  rows. The keys were distinct; this was duplicate presentation, not duplicate
  Swift identifiers. The shared reducer independently appended ToolCall and
  Link. Demand paging faithfully reconstructed both, rather than creating
  the duplicate. This does not establish which historical merge introduced it.
- The large child produced a real spilled tool result: 10,828 bytes, including
  the task wrapper. `Shown::Held` turned its reference into user-facing MIME,
  blob terminology and an identifier. No evidence showed a context-graph
  authority image escaping into the transcript.
- The macOS item renderer ignored the existing `DisplayItem.navigation`.
  The real web event stream and real TUI attach process also showed the
  tool/child pair and storage terms. This located the shared defects below
  all three renderers.
- Native scrolling upward left `followsHistory` true, since that flag describes
  the requested SDK range. `FollowEnd` called `scrollTo` on every revision.
  An external writer moved clip origin from 6,388 to 9,405 points while the
  reader was above the bottom. The old paging callback chose a new page end
  instead of preserving a visible row and pixel offset.

The simultaneous baseline FFI/store dumps, native view hierarchy and in-process
window capture are retained alongside the original PTY and web output.

## Implementation

`Link.call` records the owning spawn decision's CallId, as approved by the
owner. The kernel already has this value at spawn time. This is the only
new durable field; there is no child storage redesign or inference from tool
names, adjacency or authority JSON. PROTO is 44; the new wire corpus and view
vectors were generated by their tests, with no edits to old recordings.

The shared reducer replaces the owning tool row with Child, preserving its
key. Additional children of one call use their own link keys. Watches determine
child completion/status; completion never recreates a task card. The indexed
history retains contributing facts, stable keys and status through thinning;
old cuts still reconstruct correctly. Input recall independently retains the
original editable user command after its transcript becomes a child item.

The shared presentation shortens the child's work and result summary, and
replaces stored-output internals with `Output · N bytes` plus the shared
`Open output` label. A completed task's stored return can supply the retrievable
output reference without restoring its tool card. The FFI exposes that reference
as `Presentation.content`; its asynchronous, cancellable output fetch uses the
attached session's authority. The native app opens a sheet, the TUI opens a
scrollable output view, and the web opens its authenticated output route.
All three clients open the child's own transcript from the child affordance.

`TranscriptView` uses AppKit's NSScrollView and NSHostingView. Clip bounds track
pinning. Stable item/fragment identities and native marker frames retain a
visible anchor and offset while adjacent pages arrive. The display retains
the preceding page during delivery; it does not expand SDK history demand.
Wheel events request adjacent history at the boundary. Later-page delivery
preserves the visible item, and reaching the live bottom resumes following.
There is no per-revision scrollTo. Layout writes the clip origin only when
its calculated target differs. Main-actor store updates and transcript layout
have points-of-interest signposts.

## Native and cross-client verification

A real NSWindow hosts the production transcript in the regression test. It
populates 40 long echo turns, scrolls the actual clip view up, receives an
external writer's update and asserts origin remains within one point. It
also checks visible-anchor retention across earlier and later page delivery,
and that pinned output follows the bottom. This is a native view test, not
a simulated range-only store assertion or a manual trackpad assessment.
There is no existing XCUITest suite to extend.

Shared view vectors exercise awaited, background and parallel children,
status/results and reconstruction at all cuts. SDK tests demand child history
pages; Swift live tests assert one navigable child/no task card and fetch the
full 10,828-byte stored output. TUI tests cover navigation/output actions,
indexed card consistency, wrapping and output scrolling. Web tests cover
child links and human output presentation.

The final real-session evidence contains four Child items and zero Tool rows
for task, fork_task, background_task and a large task. The real browser DOM
contains four distinct child links; opening a child reaches its transcript,
and Open output returns all 10,828 bytes, matching the FFI fetch. The real
TUI capture shows the human output label and child actions without blob text.
Its cumulative terminal redraw stream is not used as a row-count assertion;
the simultaneous canonical FFI state and regression tests establish counts.
A background echo can legitimately emit its own assistant text.

## Release measurements

Apple M3, 16 GiB, native arm64 macOS 27.2. Both arms used release builds,
matching diagnostic instrumentation and fixture helpers. Five fresh isolated
homes per arm ran in interleaved order AB, BA, AB, BA, AB. No build, test or
profiler overlapped these accepted rounds.

Each real app session spawned 32 children with long repeated-line output, then
received 16 external turns. Every run reached parent seq 258, recorded 48
main-actor store applications and 120 native scrolling/layout/display blocks.
The app was visible and its document exceeded the viewport. Per-run medians
(and separately per-run p95s) are summarized as median [min–max] across five
rounds; p95 uses nearest rank. RSS is the app process's end-of-run ps RSS,
excluding daemon and child processes.

The main-actor measure is synchronous wall time around SessionStore.apply,
including identical signpost overhead, not exclusive CPU time or the entire
SwiftUI render pipeline. Native scroll work times scroll, layout and synchronous
window display on the main actor. It is not GPU compositor completion time.
CADisplayLink intervals separately describe callback delivery; median delivery
remains approximately 60 Hz. The native work and callback tails improved on
this workload; the store-apply saving is only about six microseconds.

RSS **increased by 30.906 MiB** at the median. The native host eagerly lays out
the bounded current/preceding display pages; it trades memory for stable native
geometry and faster scroll work here. This series does not isolate which
allocation contributes how much of the increase. No heap attribution or memory
improvement is claimed. Virtualizing that host would be additional work with
unknown savings and must preserve native anchor behavior; it was not added as
speculative hardening or as part of the separate child-storage investigation.

Command-line Instruments Time Profiler successfully recorded both real release
app PIDs, separately from timing rounds. Production Session update and Transcript
layout signposts plus the identical external Native scroll frame instrumentation
provide timing boundaries. The complete .trace packages and export tables of
contents are retained. Earlier idle sample captures are supplementary only.

The external harness is retained in both scratch source mirrors and its hashes
and executable/product-diff hashes are in accepted-provenance.json. It selects
the fixture session, performs the workload and gathers monotonic timings without
file I/O inside measured apply calls. Instrumentation is not shipped as a debug
UI or product startup behavior. Earlier pilot/measured series are retained but
excluded: setup/clock-boundary corrections preceded the accepted run. There
are no projected savings.
