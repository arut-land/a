## What changed and why

An inherited context now names an ordinary source session and frozen sequence
(`LogCut`), with its runner, effective publication identities and a reference to
the logged presentation-generation fact (`ContextCut`). A fork or model-only
side input no longer serializes projected transcript segments into content
blobs. The source JSONL is the durable transcript for both roots and children.
The app-ux owning-call `Link` and public conversation tree remain the client
relationship model.

The JSONL store retains the original file with a durable hard link at
`sessions/retained/<id>.jsonl` before publishing an admission that names it.
This is the same inode/file identity, including later appends, not a byte copy.
The retained namespace is outside catalog discovery. Removing a visible parent
or catalog entry cannot remove referenced bytes. Readers cap every operation at
the recorded sequence. Live cut readers reuse the ordinary source log and its
disposable index; if its visible name is gone, they open the retained JSONL and
rebuild missing positions. Retention publishes no second index alias. Source logs themselves contain earlier source references,
so retention is recursive. Disposable indexes can be lost and rebuilt from
ordinary sealed JSONL. No ordinary garbage collector currently deletes
unreferenced retained logs or payload blobs; this change does not introduce one.

Pin names are ordered with the existing `sys::fs::order_dir` primitive before
the referring admission's shared store barrier. On macOS that orders metadata
before the common cache flush; the other backends already sync the directory.
The source and referring log belong to the same checked store flush domain.
This preserves the publication barrier without a separate full-device flush for
each pin. The flat retained directory is established durably on the first pin;
read-only startup does not publish retention names. It does not publish a fresh
directory for every source.

Projection reads raw entries backwards with operation-scoped file handles,
selects the requested suffix, applies only edits visible at that cut, then uses
the existing transcript reducer. Sequence numbers and provider IDs stay in their
source scopes; pending exchanges remain context rather than child execution.
Runner interpretation, opaque provider state and publication identities are
preserved. Disposable publication checkpoints avoid refolding an entire prefix
when side turns request an older cut; these contain cut metadata, not projected
transcripts. A presentation cut points directly at the admitted `Extensions` or
`Spawned` fact, so cold recovery does not scan an entire prefix for metadata.
Public conversation descriptions read only the admitted request and time, and
publication folds read only inherited identities. Paging does not interpret
private source or execution authority to obtain these descriptions.

Deleted classes: persistent `ContextNode` codec, graph writer/sealing, previous
node chains, graph-root retention, presentation graph blobs/cache,
`BlobOrigin::Context`, and graph-origin attachment filtering. The traversal that
remains reads ordinary log references and transient reducer inputs; it does not
read a second persisted transcript format. `Body::cuts` exposes recursive source
retention edges separately from actual payloads in `Body::blobs`.

Kept: result/image/paste/job blobs and content addressing; projection-based
payload access checks; admission barriers; watches, inboxes and budgets;
provider-prefix compiler caches. Prefix cache identities use `LogCut` rather
than a context blob hash. Publication snapshots remain in admission authority;
admission deduplication (stage 4) was [measured and closed](admit-dedup.md).

PROTO changes **45 → 46** and JSONL format **1 → 2**, without compatibility or
migration. Version literals were bumped by the external `versions.py` script;
wire corpus v46 and shared view vectors were generated by their existing tests.
Older corpora, recorded provider cassettes and encode golden files were not
edited. Existing stores/clients need a fresh compatible pre-release build/store.

## What we over-engineered

The graph solved a real problem: the older implementation repeatedly copied
inherited transcripts into admission records. Its prepared provider-prefix
compiler solved another real problem: recompiling settled inherited messages.
Current main's context blobs are projected segments, not the primary child
session log; children already have ordinary JSONL logs.
Those improvements should not be conflated with keeping a second persistent
transcript representation. Ordinary logs already own the facts and edit order;
the graph added codecs, seals, previous/inherited/presentation edges, blob
origins, access branches and another retention vocabulary around projections of
those same facts. Retaining source bytes allows that persistence machinery to
be removed while retaining the compiler cache.

This is not evidence that all blob storage was a mistake. Large tool results,
pastes, images and job output still benefit from content addressing and bounded
wire payloads. Nor does this change explain every duplicated child UI: app-ux
already fixed the public owning-call/tree relationship before this branch.

The tradeoff is explicit: replay may decode source log entries, and retaining a
file retains bytes after an old cut as long as another name keeps that file.
This is a simpler ownership model, not automatic proof of lower CPU or minimum
retained bytes. Measurements below determine the performance verdict.

## Measurement method

Raw scripts, binaries, stopped homes, counters, native heap output and client
hashes live outside the worktree at:


`matrix.py`, `browser.mjs` and the two `ffi-*-source` helpers reconstruct the
context-graph workload: 1/4/8 roots ×32 turns, fresh/inherited/background
children, a grandchild, a real shell background job, file/skill tools and title
side conversations. Five agents stream 128 KiB and eight tools execute per root
turn. The synthetic Chat SSE server is loopback only. Both arms use
`cargo build-release -p a --features fixtures`, opt-z/fat LTO/one codegen unit
and rebuilt std, through the same external target, on an Apple M3 with 16 GiB
RAM and macOS 27.2 arm64. No release timing overlaps
builds or test suites. Five rounds alternate arm and scale order. Five further
paired 64-turn cases include the three required deep completions and provide
five rounds for the deep timing comparisons too. Streamed text contains word
separators and is exactly 128 KiB per fresh agent response. Earlier unbroken-word
payload/browser-harness diagnostics are excluded.

Before rendering consumers attach, native `heap --noContent` measures live
malloc and `proc_pid_rusage` measures daemon charged footprint and user+kernel
CPU. Late-turn CPU is the mean of the last four construction turns per case;
provider/shell/client CPU is excluded. Attach is through the public stream;
first child page is the first 64 KiB history page of a latest-turn inherited
child. Admission latency is observed root tool-response completion to publication
of that fork in the public conversation tree, including scheduler/transport
work; it is not an isolated freeze-function benchmark.

On this host the raw rusage CPU fields are Mach ticks. `cpu-timebase.json`
records the native 125/3 nanoseconds-per-tick conversion, cross-checked against
`ps` accumulated CPU. Accepted records explicitly declare `cpu_units` as
`nanoseconds` after applying that conversion. Earlier diagnostic records lack
that marker and are excluded. Monotonic wall-clock timings, heap and charged
memory need no correction.

After construction, actual PTY TUIs, one public Rust FFI Session process per
root, and Chrome tabs through one `a web` server attach to every root. Each
root uses a separate authenticated browser context. An extra live turn verifies streaming to
all three consumer types. Tool counts and durable outcomes are checked. Warm
and fresh-daemon raw history-page hashes and canonical FFI tail-state hashes
must match. Restart time includes CLI startup, daemon restart and `ls`.
Retained bytes count sessions, blobs and the catalog index after the live turn
and restart, deduplicating file identities so hard links count once. This is
logical unique-file size, not physical allocated blocks. Diagnostic smoke runs
are excluded. Successful homes are losslessly archived after daemon shutdown,
preserving original files and hard links; counters and client hashes stay beside
each archive. Historical context-graph numbers are not reused as observations.

An earlier harness multiplexed all FFI sessions over one SDK client and saw one
initial attach connection closure on main at eight roots. Those cases are kept
as diagnostics and excluded; the accepted cohort uses the historical workload's
separate FFI processes. An intermediate candidate also had an initial FFI
connection closure with no history delivered; this failed correctness check
is retained under `before-description-*`, not counted in the accepted cohort.
All 40 final cases passed. Intermediate product versions and browser/payload setup
experiments are likewise excluded. Exclusion is by source/method version or a
failed correctness check, never by a timing result.

Retained log/payload collection remains absent, as before for blobs. A future
collector must start at live roots, follow `Body::cuts` recursively and sweep
only after preserving source prefixes and their payloads. Without collection,
long-lived usage retains unreferenced bytes. This is expected under the current
store, not speculative hardening added here. Collector design and crash-safe
reclamation are separate work.

One hypothetical failure path was left for owner review rather than hardened:
if the process exits or directory ordering fails after creating the hard link, a
retry finds that name and returns without repeating its directory barrier.
Losing referenced bytes would additionally require power loss before the name
became durable and removal of the visible source name. There is currently no
ordinary visible-log deletion path, so this conjunction appears unlikely; it
has not been reproduced. Repeating the barrier on an existing retention name
would cost an extra directory sync per cut, or require tracking confirmed pins.
No speculative retry/durability state machine was added.
